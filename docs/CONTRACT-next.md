# API contract for the remaining features (agreed up front so three teams can build in parallel)

All routes are under the existing NestJS API (`apps/api`). JSON everywhere. Errors carry a stable `code`. Money is `{ minor: int, currency: 'USD'|'ZAR' }` or `xxxMinor` ints. Providers are identified by `providerId` (the `providers.id`, available on `req.user.providerId` via the `@CurrentUser('providerId')` decorator); people by `userId`.

## 1. Markets: emergency number

`GET /markets` items gain `emergencyNumber: string` from a new `countries.emergency_number` column (migration 023). ZA `10111`, ZW `999`. The Dart `Market` model gains `emergencyNumber` (default `'112'` if absent). Both apps use it instead of the hard-coded `10111`.

## 2. Reviews: "have I reviewed this booking" and the double-sided flow

Existing: `POST /bookings/:id/review { rating 1-5, tags: string[], comment? }` works for the client (direction `client_to_provider`) and for the provider (direction `provider_to_client`); only on a `completed` booking.

New: every booking JSON (`mapBooking` output, used by `GET /bookings`, `GET /bookings/:id`, the provider schedule endpoints) gains `reviewedByMe: boolean` — true when a `reviews` row exists for that booking authored by the caller. Both apps use it to show "Rate" vs "Rated".

Review tags are free strings. The client app offers: `On time`, `Great cut`, `Friendly`, `Clean kit`, `Professional`, `Would rebook`. The provider app offers: `On time`, `Clear directions`, `Friendly`, `Respectful`, `Easy to find`, `Would work again`.

## 3. Invoices (SARS / ZIMRA split invoicing)

On `completed` (inside the completion transaction, after the ledger group), two invoice rows are written to a new `invoices` table (migration 023):

- `provider_to_client`: issuer = provider, recipient = client. Lines: each service, add-ons, travel. Total = subtotal + addons + travel (what the client paid minus the platform fee).
- `platform_to_provider`: issuer = Freshly, recipient = provider. Lines: marketplace commission, platform service fee; VAT shown as a separate line computed from `vat_on_fees_minor`; total = commission + service fee (these amounts are VAT-inclusive, the VAT line is informational, labelled with the market's `vat_label`).

Columns: `id uuid pk, booking_id, kind invoice_kind_enum ('provider_to_client','platform_to_provider'), number text unique (format `FR-ZW-2026-000001`, per country, sequential via a `invoice_sequences(country_code, year, last)` table), issued_at, currency, lines jsonb [{label, amountMinor}], subtotal_minor, vat_minor, total_minor, issuer_name, issuer_detail, recipient_name, recipient_detail`. `issuer_detail`/`recipient_detail` are short text (city, phone last 4). Never store a full phone number or ID number on an invoice row.

Endpoints:
- `GET /bookings/:id/invoices` → `[{ id, kind, number, issuedAt, currency, totalMinor }]`. The client sees only `provider_to_client`; the provider sees both; admins see both.
- `GET /invoices/:id.pdf` → `application/pdf`, same visibility rule. Rendered with `pdfkit` (add the dependency; it needs no network and no browser). One page: issuer block, recipient block, number and date, a lines table, subtotal / VAT / total, footer "Generated by Freshly".

Dart: `Invoice` model `{id, kind, number, issuedAt, currency, totalMinor}` and `FreshlyApi.invoices(bookingId)` plus `FreshlyApi.invoicePdfUrl(id)` returning the absolute URL (the app opens it with `url_launcher` after fetching with the auth header: simplest is `FreshlyApi.downloadInvoice(id)` returning bytes, saved to a temp file and opened with `open_filex` or shared with `share_plus`; pick `share_plus` which is already common). If `share_plus` is not in the pubspec, add it to both apps.

## 4. Salon staff management (business_mode = 'salon')

Model: a salon is a provider with `business_mode = 'salon'`. Staff are providers with `business_mode = 'salon_staff'` and `salon_parent_id = <salon provider id>`. Staff share the salon's menu, service area and location; they do not appear in discovery on their own; money always goes to the salon's wallet (the booking's `provider_id` stays the salon). A booking can be assigned to a staff member via a new nullable column `bookings.assigned_staff_id uuid references providers(id)` (migration 023). The assigned staff member can run that job exactly as the salon could: `POST /bookings/:id/status`, `verify-pin`, `complete`, chat, `addons`, and sees it in their schedule/job views. Implement one helper `canOperate(booking, providerId)` = `booking.provider_id === providerId || booking.assigned_staff_id === providerId` and use it everywhere the service currently checks `booking.provider_id !== providerId` for job operations. The salon owner keeps full access.

Invites are by phone number, so a staff member who has never used Freshly can be invited.

Tables (migration 023): `staff_invites (id uuid pk, salon_provider_id, phone_e164, status staff_invite_enum ('pending','accepted','cancelled'), created_at, accepted_at, accepted_provider_id null)`.

Endpoints, salon side (require role provider AND the caller's provider `business_mode = 'salon'`, otherwise `salon_only` 403):
- `GET /providers/me/staff` → `[{ id, kind: 'staff'|'invite', displayName?, phone (masked, e.g. "+263 77 ••• 0003"), status: 'active'|'pending', jobsThisWeek: int, completedJobs: int }]`
- `POST /providers/me/staff/invites { phone }` → `{ id, status: 'pending' }`. Refuse `already_staff` if that number is already this salon's staff; refuse `invite_pending` if one is pending; a number that belongs to a provider with their own business is refused `has_own_business`.
- `DELETE /providers/me/staff/:id` → cancels a pending invite, or removes an active staff member (their provider row becomes `business_mode = 'solo'`, `salon_parent_id = NULL`, `is_online = false`; any of their open assigned bookings are un-assigned back to the salon).
- `POST /bookings/:id/assign { staffId }` (salon owner of the booking, booking status in authorized/accepted/en_route) → `{ assignedStaffId }`. `staffId` must be an active staff member of this salon. `{ staffId: null }` un-assigns.

Endpoints, invitee side (any signed-in user; this is how someone with no provider row joins):
- `GET /auth/staff-invites` → `[{ id, salonName, salonSuburb }]` pending invites for the caller's phone.
- `POST /auth/staff-invites/:id/accept` → same response shape as `POST /auth/become-provider` (a session carrying the provider role). Creates the provider row if absent (`business_mode = 'salon_staff'`, `salon_parent_id`, `display_name` = user's full name, country/service area/base location copied from the salon, `kyc_status = 'pending'`), or converts an existing solo provider that has no completed jobs; a provider with completed jobs is refused `has_own_business`. Marks the invite accepted.

Dispatch: a salon's job offers go to the salon owner's device as today. Nothing changes there.

Booking JSON gains `assignedStaffId: string|null` and `assignedStaffName: string|null`. The provider schedule endpoints (`GET /providers/me/schedule`, `schedule/upcoming`, `schedule/completed`) return, for a staff member, the bookings assigned to them; for a salon owner, everything on the salon including who it is assigned to.

Dart (`freshly_core`): `StaffMember {id, kind, displayName, phoneMasked, status, jobsThisWeek, completedJobs}`, `StaffInvite {id, salonName, salonSuburb}`, `FreshlyApi.myStaff()`, `inviteStaff(phone)`, `removeStaff(id)`, `assignBooking(bookingId, staffId?)`, `staffInvites()`, `acceptStaffInvite(id)`; `Booking` gains `assignedStaffId`, `assignedStaffName`, `reviewedByMe`.

KYC: staff must verify identity like any provider before they can be assigned a job (`assign` refuses `staff_unverified`). Their own wallet is never used.

## 5. SOS stand-down

Existing `POST /safety/sos/:id/abort` (see `FreshlyApi.abortSos`). After a successful SOS the app shows a persistent sheet with "I am safe now" that calls it; the response team sees the stand-down in the ops console (already does).
